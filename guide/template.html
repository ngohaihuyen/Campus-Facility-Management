University Facility Booking System

Building the full app with MySQL, Node.js and plain HTML

A basic, student-friendly booking system built on the team's own database schema, workflow diagram and meeting decisions: 3 SQL files, a 7-file Express API, and 9 plain HTML pages served by that API.

The workflow the code follows

This is the team's swimlane diagram (User, System, Admin), turned into API calls.

flowchart TD
  A[Register as student / Log in] --> B{University email?}
  B -- No --> X[Show error]
  B -- Yes --> C{Role?}
  C -- ADMIN --> AD[Admin home]
  C -- STUDENT / TEACHER / STAFF --> U1[View rooms, search, filter]
  U1 --> U2[Room details]
  U2 --> U3[Choose date + one 30-minute slot]
  U3 --> D{Time conflict?}
  D -- Yes --> U3
  D -- No --> U4[Enter purpose - required]
  U4 --> U5[Send request: status PENDING]
  U5 --> R[Admin checks user, room, date, time, purpose]
  AD --> R
  R --> E{Approve?}
  E -- Yes --> OK[APPROVED]
  E -- No --> NO[REJECTED]
  E -- No action --> P[stays PENDING]

Booking statuses

PENDING→APPROVED·PENDING→REJECTED
PENDING / APPROVED→CANCELLED

CANCELLED was added for three cases: the user cancels, a teacher takes the slot, or the admin closes the room.

4.1db.js: talking to MySQL

Every other file uses just two helpers:

how to use them
// SELECT -> array of rows
const rooms = await query('SELECT * FROM facilities WHERE id = :id', { id: 5 });

// INSERT / UPDATE -> { insertId, affectedRows }
const result = await query('UPDATE users SET is_active = 0 WHERE id = :id', { id: 5 });
if (result.affectedRows === 0) { /* nothing was changed */ }

// several statements: all saved together, or none
await transaction(async (q) => {
  await q('...');
  await q('...');
});
Always use :parameters

Never write `... WHERE email = '${email}'`. Putting user text directly into SQL makes SQL injection possible.

Students register themselves; teacher, staff and admin accounts are created by the admin (POST /api/admin/users). Registering needs the student code, logging in does not:

4.3bslots.js and rules.js: the times and the rules

A day is cut into 28 slots of 30 minutes: 07:01–07:30, 07:31–08:00, … 20:31–21:00. One booking is exactly one slot, so two bookings can never overlap by accident, and the user picks a slot from a list instead of typing a time.

4.4routes/facilities.js: view, search, filter, details

The (:search IS NULL OR ...) pattern means “skip this filter if it wasn't sent”. COALESCE(f.allowed_roles, c.allowed_roles) takes the rule of the room, or the rule of its room type when the room has none; can_book then tells the frontend whether the logged-in user may book it. The availability endpoint returns all 28 slots with their status (Free / Waiting for approval / Booked / Closed) plus canTakeOver, which is true when a teacher may take a slot a student booked.

4.5routes/bookings.js: the core

checkBookingInput() first checks everything that doesn't need the database: the date, that the time is a real slot, and the purpose. Then one transaction runs six steps:

  1. Lock the room with SELECT ... FOR UPDATE.
  2. Check that the user's role may book this room (room rule first, then room type).
  3. Find overlapping bookings.
  4. Apply the teacher priority rule, or refuse and show the taken time.
  5. Save the new booking as PENDING.
  6. Cancel any student bookings that were replaced.
the overlap check
WHERE b.facility_id  = :facilityId
  AND b.booking_date = :bookingDate
  AND b.status IN ('PENDING', 'APPROVED')
  AND b.start_time < :endTime     -- other booking starts before mine ends
  AND b.end_time   > :startTime   -- and ends after mine starts
-- 10:01-10:30 vs 10:31-11:00:  10:31 < 10:30 is false  →  no overlap (allowed)

Why the lock? Without it, two students clicking “Book” in the same second could both pass the overlap check and both be saved. FOR UPDATE makes the second request wait until the first one is done. Storing the time to the second doesn't prevent this; only the lock does. We tested it: 10 requests at once, and exactly 1 was saved.

{{FILE:backend/src/routes/bookings.js|src/routes/bookings.js|Rules, create, my bookings, cancel}}

4.6routes/admin.js

Admins review bookings (only PENDING ones), manage rooms and manage users. When a room is closed or deleted, its future bookings are cancelled automatically. Because there is no registration page, POST /admin/users is where accounts are created; after that the admin only changes the role or locks the account. A room's capacity is checked here too: a whole number from 1 to 300.

5.1common.js: shared by every page

  • api(method, url, body) calls the backend and adds the login token automatically. If the token has expired, it sends the user back to the login page.
  • requireLogin('ADMIN') protects a page and draws the navigation bar for the user's role.
  • esc(text) must wrap every value from the database before it goes into innerHTML. It stops users from injecting HTML or scripts.

Acceptance checklist

  • Registering with anhnq2410099@usth.edu.vn → 201, role STUDENT
  • Registering with huydt@usth.edu.vn (no student code) → 400
  • Logging in with a Gmail address → 400 “Use your university email…”
  • A time that is not a slot (10:00–12:00) → 400 “Choose one time slot…”
  • Booking a taken slot → 409 with the taken time; the next slot → 201
  • Booking with no purpose → 400
  • Student books the Teacher Meeting Room (room type rule) → 403
  • Student books Chemistry Lab D101 (rule for that one room) → 403
  • Adding a room with capacity 400 or −5 → 400
  • Admin creates an account with a Gmail address → 400; with a university email → 201
  • Teacher books over a student more than 24h ahead → 201; the student's booking becomes CANCELLED with a note
  • Rejecting without a note → 400; reviewing the same booking twice → 409
  • Room set to UNAVAILABLE → its future bookings become CANCELLED
  • Locked user → 403
  • Race test → exactly one 201
